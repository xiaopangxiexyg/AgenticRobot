# Core merge acceptance: 5–8 minute scope

The user authorized large reductions of routine tests on 2026-11-01. The target
is final merge-feedback invocation time for every subsequent routine merge.
The user clarified that retaining old long matrices as mandatory development
work does not satisfy the goal. Retire redundant or over-expensive coverage
and preserve core behavior. Production control, physics rates, limits,
hardware permissions and evidence failure semantics are unchanged.

## Why the set changes

The complete green input `d92d01f3e287803163e8060ae11bec8d7148fdfc` used 1,021
modules and 1,201 targets. Four pytest shards took 1,540.459 seconds of elapsed
envelope and 4,214.182 seconds of ordinary testcase work. Five new native
grasp/query/lift/carry/release scenarios alone consumed about 673 seconds.
Balancing those shards cannot reduce this whole workload to five minutes on a
memory-safe pair of workers.

`scripts/pytest_core.py` is an explicit responsibility inventory. It is not
generated at runtime from durations, a filename keyword, `optional`, or a
deadline. Whole modules cover reusable contracts and safety/lifecycle reducers;
mixed modules keep core families. New functions inside a core module remain
selected unless separately reviewed as extended. New owner modules must be
classified when they introduce a core invariant. Timings in the policy only
balance work; they never decide whether a test runs.

## Callers and implementation

`run_merge_acceptance.sh` is a thin `--core` call into the existing complete
runner. Four module-isolated batches use two workers; registered heavy native
owners alternate with contract batches and do not run on both workers at once.
On the guarded local merge host, an explicit eight-batch, four-worker setting
runs at most two native batches at once; `tests/README.md` records its memory
envelope and measurement.
Small handwritten models can still run in the contract batch.
Shorter processes bound native retention without changing GC. Short TMPDIR,
private caches, native heap release,
interruption cleanup and non-overwriting JUnit publication share one
implementation. `run_full_acceptance.sh` without this flag still runs the
complete set; `--changed-since` retains its existing independent meaning.

The core plan lists selected and omitted identities and the report is
`merge-core-acceptance.xml`, explicitly scoped to a clean tested commit.
Every subsequent routine merge uses this one core gate, without automatically
stacking fast-feedback, motion or full acceptance. For concrete unresolved
behavior, choose the smallest check that answers the question. Do not impose
the old complete owner matrices merely by directory or move their recurring
cost into development. Timeouts, test/resource/cleanup failures remain failures
or incomplete runs. Selection is not permission to integrate or move a branch.
Existing Harness full Profiles need an explicit configuration-owner migration;
they are not reconfigured or silently bypassed here.
