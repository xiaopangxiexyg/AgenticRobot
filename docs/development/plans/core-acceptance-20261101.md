# Core merge acceptance: 5–8 minute scope

The user authorized large reductions of routine tests on 2026-11-01. The target
is final merge-feedback invocation time, with complete matrices selected by
change or run separately. Production control, physics rates, limits, hardware
permissions and complete-suite evidence contracts are unchanged.

## Why the set changes

The complete green input `d92d01f3e287803163e8060ae11bec8d7148fdfc` used 1,021
modules and 1,201 targets. Four pytest shards took 1,540.459 seconds of elapsed
envelope and 4,214.182 seconds of ordinary testcase work. Five new native
grasp/query/lift/carry/release scenarios alone consumed about 673 seconds.
Balancing those shards cannot reduce this whole workload to five minutes on a
memory-safe pair of workers.

`scripts/pytest_core.py` is an explicit responsibility inventory. It is not
generated at runtime from durations, a filename keyword, `optional`, or a
deadline. Whole modules cover reusable contracts and safety/lifecycle reducers;
mixed modules keep core families. New functions inside a core module remain
selected unless separately reviewed as extended. New owner modules must be
classified when they introduce a core invariant. Timings in the policy only
balance work; they never decide whether a test runs.

## Retained meaning

- Shared motion/schema, authority/admission, reference/receipt, limits and
  action-composition contracts.
- B601 cancel/withdraw/lease, missing dispatch, bad receipt, raw speed and
  feedback-gap protection, explicit return/disable confirmation; a complete
  small native cycle remains. Long plant sweeps are not substituted for these
  failures or vice versa.
- Target pending/active continuation, active-envelope restore refusal, source
  isolation, backend exceptions and capture/close fencing; cheap pure
  checkpoint codecs and owners remain.
- Temp learning action ownership, positive-z vs zero-action behavior,
  constrained XY, settled reset/first step, and pure reward/configuration
  assertions. Native profile feasibility remains separate.
- Neutral Gateway identity/admission, bounded operation state, transport and
  artifacts; real qref consumption, cancellation/contact rejection, retained
  grasp pairing and an authenticated observed-point move.
- Actual release/held-object observation and transport predicates, including
  contact loss, unknown contact, sampling gaps and stable-support windows.
- Dataset contracts, real transaction/rollback/interruption/worker lifecycle
  tests; low-cost invalid-input matrices remain useful even when numerous.

## Coverage that leaves the routine set

| Family | Disposition and cost |
| --- | --- |
| Complete automatic/manual grasp, tilted placement and changed-support tasks | Extended physical scenarios, not equivalent duplicates. Related grasp/release/contact/scene changes must exercise them. Core no longer proves full physical task success for unrelated changes. |
| Multi-centre calibration and stiction/residual/friction/frequency sweeps | Extended B601 qualification. Core loses routine cross-centre and long synthetic-plant interaction coverage, retains short original-owner success/failures. |
| Repeated native profile/side/task scoring and cold-cache scenarios | Extended consumer/model matrix; short native wiring and original strict guards remain core. |
| All native scene offsets and full learning profile oracles | Extended scene/learning suite. Cheap materialization/configuration and action/success predicates remain. |
| Full native checkpoint alias, metadata, observation and state matrix | Extended recovery suite, retaining all original cases. A short restore does not prove every lifecycle cut or owner swap. |
| Historical runtime binding checks against already-frozen Git trees | Extended historical compatibility. Current binding must still match exact current inputs. |
| Provider/profile-specific application and perception matrices | Owner-focused evidence when those semantics change. Neutral wire and shared artifact rules remain core; core does not prove every concrete provider. |

The first implementation removes these responsibilities from the routine Run,
without moving test files under active peer ownership or deleting unique
scenarios. Full owner tests and `run_full_acceptance.sh` preserve their actual
assertions. Physical deletion of equivalent duplicates is a later coherent
change only after moving any unique failure assertion; it is not needed to
claim a lower routine runtime. No new tests or production validators are added.

## Callers and implementation

`run_merge_acceptance.sh` is a thin `--core` call into the existing complete
runner. Four module-isolated batches use two workers; registered heavy native
owners alternate with contract batches and do not run on both workers at once.
Small handwritten models can still run in the contract batch.
Shorter processes bound native retention without changing GC. Short TMPDIR,
private caches, native heap release,
interruption cleanup and non-overwriting JUnit publication share one
implementation. `run_full_acceptance.sh` without this flag still runs the
complete set; `--changed-since` retains its existing independent meaning.

The core plan lists selected and omitted identities and the report is
`merge-core-acceptance.xml`, explicitly scoped to a clean tested commit.
Selection is not an automatic integration-permission or change-impact oracle.
The integration owner still selects required extended evidence for the exact
combined source. Existing Harness full Profiles are not reconfigured here.
